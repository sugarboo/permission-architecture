授权流程导览

本版不再把 HTTP Method + URL 当作权限标识。后端、前端和权限中心统一围绕稳定业务权限编码，例如 information.customer.create。
建议体验路径：定义应用与模块 → 配置菜单 → 定义业务功能和资源 → 创建角色 → 配置数据/字段范围 → 分配用户 → 权限模拟与审计。
1

应用与模块

用 APPLICATION 承载信息、供应链、设计师、财务、人力资源等中台大板块；MODULE 只负责业务分组。
2

菜单入口

菜单负责导航，可绑定一个最小进入功能编码，但不作为后端安全边界。
3

业务功能

查看、新增、编辑、导出等能力使用稳定 Function Code，并直接作为后端鉴权标识。
4

业务资源

注册业务对象、字段、文件、报表、工作流动作和任务；具体记录只在运行时校验。
5

角色授权

给角色勾选菜单与功能，并配置数据范围、字段策略和成员。
6

模拟验证

验证张三是否拥有查看客户功能、目标客户是否在其数据范围、手机号最终如何返回。

核心概念对照

概念只回答一个问题企业示例
APPLICATION属于哪个中台大板块信息板块 / 供应链板块 / 财务板块
MODULE板块内部如何分组客户管理 / 供应商管理 / 应付管理
MENU用户从哪里进入客户列表
FUNCTION用户可以执行什么动作information.customer.read / create / export
RESOURCE动作作用于什么业务对象客户、手机号字段、合同附件
DATA POLICY可以处理哪些具体记录本人及协作客户 / 本部门及下级
FIELD POLICY记录内部哪些内容可见/可改/可导出手机号脱敏、利润率隐藏
废弃的设计：不再维护“接口权限资源”、接口字段映射或角色 → URL 权限关系。接口 URL 只是实现细节；后端方法直接声明业务权限，例如 @RequirePermission("information.customer.update")。

用户管理

用户即企业员工，同时承担登录主体和权限主体；直接维护组织、岗位、直属上级和角色授权。
姓名账号组织 / 部门岗位角色状态最近登录操作

组织与岗位

OrgUnit 统一承载集团、区域、公司、部门、团队；岗位独立存在，并可配置岗位自动角色。

角色管理

角色是可复用的权限集合：菜单 + 业务功能 + 数据范围 + 字段策略；不做角色继承，也不单独引入数据角色。
角色名称编码类型应用成员菜单权限点策略风险操作
编辑角色 草稿

应用与模块

APPLICATION 对应中台大板块；MODULE 只用于板块内业务域分组，不直接参与运行时鉴权。

业务功能

FUNCTION 是前后端共享的稳定授权标识。URL、Controller 方法名或按钮文案变化，不应改变 Function Code。
功能稳定权限编码应用 / 模块业务对象动作风险角色引用状态操作

后端使用方式

@RequirePermission("information.customer.create") public Result createCustomer(...) { // URL 只是技术实现；真正授权依据是稳定业务权限编码 }

菜单管理

维护目录、页面、路由和最小进入功能；菜单只负责导航入口，真正的安全边界是后端 Function Code 鉴权。

资源中心

只注册真正需要被业务权限保护的对象。APPLICATION、MODULE、MENU 已有独立模型；接口 URL 不注册成权限资源；具体记录只在运行时作为资源实例出现。
业务对象字段文件 / 报表 / 工作流 / 任务

数据权限

第一版优先采用固定范围模板：NONE、SELF、SELF_AND_SHARED、DEPT、DEPT_AND_CHILD、CUSTOM、ALL；复杂 ABAC 只在确有需求时扩展。
